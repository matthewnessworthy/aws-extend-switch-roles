<objective>
Automate the AESR release pipeline end-to-end via GitHub Actions so that pushing a `v*.*.*` tag to the fork remote drives: build -> unit tests -> emulator tests -> store-zip packaging -> source-zip packaging -> GitHub Release with all artifacts attached -> conditional publish to Chrome Web Store, Firefox AMO, and Edge Add-ons. Prereleases (`v*-rc*`, etc.) skip store publish.

Purpose: Today the release flow is fully manual (Phase 5 generated `aesr-source.zip` by hand; archive zips need a local build; nothing pushes to stores). The user wants every mechanizable step in CI so the only manual work that remains is the truly manual stuff (store-account registration, listing-copy edits, handling rejections).

Output: One reproducible source-zip script, one tag-triggered release workflow with conditional store-publish jobs, and a RELEASE.md runbook covering secrets, manual residue, and rollback.
</objective>

<task type="auto">
  <name>Task 2: Tag-triggered release workflow with conditional store publish</name>
  <files>.github/workflows/release.yml</files>
  <action>
Create `.github/workflows/release.yml`. Single file. Structure:

Trigger: `on.push.tags: ['v*.*.*', 'v*-rc*', 'v*-beta.*', 'v*-alpha.*']` + `workflow_dispatch` with one input `tag` (description: "Tag to release, e.g. v6.3.0; leave blank to use the pushed tag"). Workflow-level `permissions: contents: write` (required to create GH Releases). `concurrency: { group: 'release-${{ github.ref }}', cancel-in-progress: false }` — do NOT cancel in-progress releases.

Compute one workflow-level env `IS_PRERELEASE`: true if the tag matches `-rc`, `-beta.`, `-alpha.`, or contains a hyphen after the version triple. Use a `release` job that emits `prerelease` and `version` outputs derived from `github.ref_name` (strip leading `v`).

Job 1: `build-and-release` (`runs-on: ubuntu-latest`). Steps:
1. `actions/checkout@v4` with `ref: ${{ inputs.tag || github.ref }}` (so `workflow_dispatch` with a tag input checks out that tag).
2. `actions/setup-node@v6` with `node-version: 24` and `cache: 'npm'`.
3. `npm ci`.
4. Cache Playwright browsers — copy the cache step from `.github/workflows/test.yml` verbatim (same key, same restore-keys) so we share the cache with test.yml.
5. `npx playwright install --with-deps` gated on `steps.cache-playwright-browsers.outputs.cache-hit != 'true'` (same pattern as test.yml).
6. `npm test` (mocha unit tests).
7. `xvfb-run npm run test_emulator` (Playwright emulator tests).
8. Verify tag matches package version: read `node -p "require('./package.json').version"`, compare against `${{ github.ref_name }}` with leading `v` stripped — fail the job with a clear error if mismatched (prevents accidentally releasing the wrong version because a tag was pushed against an unbumped commit).
9. `npm run archive` (produces `dist/chrome/aesr-chrome-<v>.zip` and `dist/firefox/aesr-firefox-<v>.zip`).
10. `npm run archive:source` (produces `dist/aesr-source-<v>.zip`).
11. Copy chrome zip as edge zip: `cp dist/chrome/aesr-chrome-${VERSION}.zip dist/aesr-edge-${VERSION}.zip` (Edge accepts the Chrome MV3 zip as-is; an explicit edge-named artifact makes the GH Release inventory self-documenting and lets the edge publish job reference a stable name).
12. `actions/upload-artifact@v4` — upload all four zips as artifact `release-zips-${{ github.ref_name }}` (retention 30 days) so the store-publish jobs can `download-artifact` them.
13. `softprops/action-gh-release@v2` — create/update the GitHub Release for the tag. `prerelease: ${{ env.IS_PRERELEASE == 'true' }}`. Attach all four zips (use a `files:` glob pointing at the four explicit paths, not a wildcard, to avoid accidentally attaching the unrenamed chrome zip twice). `generate_release_notes: true`.

Job 2: `publish-chrome`. `needs: build-and-release`. `if: needs.build-and-release.outputs.prerelease != 'true' && vars.CHROME_EXTENSION_ID != ''` — gate on a public `vars` value (CHROME_EXTENSION_ID is not secret) plus secret presence checked inside the step. Steps: download the artifact, then run `PlasmoHQ/bpp@v3` with only the chrome `keys` populated (JSON inline via `${{ secrets.CHROME_PUBLISH_KEYS }}` — a single JSON blob is operationally simpler than 4 separate secrets and matches PlasmoHQ/bpp's documented input shape). Add a guard step before bpp that fails with a clear message if `secrets.CHROME_PUBLISH_KEYS` is empty — this catches the case where vars.CHROME_EXTENSION_ID is set but the keys secret isn't.

Job 3: `publish-firefox`. Same shape as publish-chrome but gated on `vars.FIREFOX_EXTENSION_ID` and `secrets.FIREFOX_PUBLISH_KEYS`. Pass the chrome-bpp-equivalent JSON for firefox, including `sourceZip: aesr-source-<v>.zip` (AMO requires source for any extension with bundled/minified output — this project does Rollup bundling, so source is mandatory).

Job 4: `publish-edge`. Same shape, gated on `vars.EDGE_PRODUCT_ID` and `secrets.EDGE_PUBLISH_KEYS`. Uses the `aesr-edge-<v>.zip` artifact.

For all three publish jobs: `if:` expression uses `needs.build-and-release.outputs.prerelease != 'true'` first so they short-circuit on prereleases.

Pin all third-party actions to a major version tag (`@v4`, `@v6`, `@v2`, `@v3`) — match the style used by `.github/workflows/test.yml` so we don't introduce a SHA-pinning convention only here. (If a strict pinning policy is desired later, it can be applied repo-wide as a separate concern.)

No `--dev` builds in this workflow; release artifacts are production builds only.
  </action>

  <name>Task 3: RELEASE.md operator runbook</name>

  <action>
Create `RELEASE.md` at repo root covering exactly these sections in this order:

1. **How to release** — One paragraph: bump version in `manifest.json` + `package.json` + `package-lock.json`, commit, `git tag -a v<X.Y.Z> -m '...'`, `git push fork main && git push fork v<X.Y.Z>`. Note that the workflow triggers on tag push; the GH Release page link will appear under repo Releases when the workflow finishes.

2. **Tag conventions** — `vX.Y.Z` = production release (publishes to stores if secrets configured). `vX.Y.Z-rc.N`, `vX.Y.Z-beta.N`, `vX.Y.Z-alpha.N` = prerelease (creates GH Release marked prerelease; store-publish jobs skip). Use prereleases to dry-run the build pipeline before a real release.

3. **Repository secrets and variables** — Table with three rows (Chrome / Firefox / Edge). Columns: Store, Repo variable (vars.*), Secret (secrets.*), Where to obtain. Fill in:
   - Chrome: `vars.CHROME_EXTENSION_ID` (Chrome Web Store Developer Dashboard -> the extension's edit page -> URL or "Item id" field). `secrets.CHROME_PUBLISH_KEYS` (Google Cloud Console: create an OAuth2 client with Chrome Web Store API access; the secret is a JSON blob `{ "clientId": "...", "clientSecret": "...", "refreshToken": "..." }` — link to https://developer.chrome.com/docs/webstore/using-api/ for the full flow).
   - Firefox: `vars.FIREFOX_EXTENSION_ID` (the AMO listing's add-on ID, usually a UUID; matches the `browser_specific_settings.gecko.id` in `manifest_firefox.json`). `secrets.FIREFOX_PUBLISH_KEYS` (AMO Developer Hub -> Manage API Keys; JSON `{ "issuer": "user:...", "secret": "..." }` — link to https://addons.mozilla.org/en-US/developers/addon/api/key/).
   - Edge: `vars.EDGE_PRODUCT_ID` (Microsoft Partner Center -> the add-on's product page; product ID is shown in URL). `secrets.EDGE_PUBLISH_KEYS` (Partner Center -> API access; JSON `{ "clientId": "...", "clientSecret": "...", "accessTokenUrl": "..." }` — link to https://learn.microsoft.com/en-us/microsoft-edge/extensions-chromium/publish/api/using-addons-api).
   Add a short note: "Publish jobs skip when either the var or the secret is missing — you can roll out one store at a time."

4. **What still must be manual** — Bulleted list, accurate to scope:
   - Initial store-developer registration: Chrome Web Store ($5 one-time fee), Firefox AMO (free), Edge Add-ons via Microsoft Partner Center (free).
   - First-time submission of the extension to each store (the publish API updates existing listings; it does not create new ones).
   - Editing the store listing copy (description, screenshots, category, support URLs). Screenshots committed to the repo could in theory be auto-uploaded, but listing copy edits go through each store's dashboard.
   - Privacy policy hosting and DSA trader-info attestation.
   - Responding to store reviewer feedback / rejections.
   - Source-bumping `manifest.json` + `package.json` + `package-lock.json` and creating the git tag (this is intentionally kept manual — see "How to release").

5. **Rollback** — Three scenarios:
   - **Tag pushed but build failed before GH Release was created**: Fix the issue, re-tag (`git tag -d v<X.Y.Z> && git push fork :refs/tags/v<X.Y.Z>` to delete remotely, then re-tag and re-push), or re-run via `workflow_dispatch` with the same tag.
   - **GH Release published but you don't want to publish to stores yet**: Stores only publish on non-prerelease tags. If you tagged `vX.Y.Z` instead of `vX.Y.Z-rc.1` by mistake, the publish jobs may have already started — cancel the workflow run from the Actions UI immediately. If a chrome/firefox/edge publish API call already completed, you need to use that store's dashboard to unpublish (no API rollback exists; document this constraint clearly).
   - **Stuck release-zips artifact**: Artifacts retain for 30 days. Re-run the build via `workflow_dispatch` against the same tag to regenerate.

6. **Workflow file** — One line: see `.github/workflows/release.yml`.

Keep the document terse and operationally-focused. No marketing tone, no preamble, no emoji. Match the spare, direct style of `BUILD.md`.
