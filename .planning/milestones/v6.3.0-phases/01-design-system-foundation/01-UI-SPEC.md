## Spacing Scale

Hand-derived from Cloudscape `visual-refresh/spacing.ts` (STACK.md). The GSD 8-point scale is the public contract; Cloudscape's `space-s` (12px) and `space-l` (20px) are the only sub-multiples-of-4 anchors carried over because they define the AWS-native field/button/container rhythm. All values are multiples of 4 **except** the two listed exceptions, each justified below.

| Token (CSS var) | Value | Cloudscape token | Usage |
|-----------------|-------|------------------|-------|
| `--space-xxxs` | 2px | space-xxxs | Hairline insets only (exception — see below) |
| `--space-xxs` | 4px | space-xxs | Icon gaps, list-item vertical padding, badge inset |
| `--space-xs` | 8px | space-xs | Compact element spacing, inline gaps |
| `--space-s` | 12px | space-s | Field vertical rhythm, tight stack gap (exception — see below) |
| `--space-m` | 16px | space-m | Default element spacing, container content gap |
| `--space-l` | 20px | space-l | Button horizontal padding, container horizontal padding, list-item horizontal padding |
| `--space-xl` | 24px | space-xl | Section padding |
| `--space-xxl` | 32px | space-xxl | Layout gaps, major section breaks |
| `--space-xxxl` | 40px | space-xxxl | Page-level spacing |

**GSD 8-point mapping (60/30/10 framing reference):** 4 (`xxs`) · 8 (`xs`) · 16 (`m`) · 24 (`xl`) · 32 (`xxl`) · 40 (`xxxl`) — the scale caps at 40. No Phase-1 primitive needs a 48/64 token; if a later surface phase requires one it declares it explicitly rather than composing tokens at use sites.

**Exceptions (justified):**
- `--space-xxxs` = **2px** — Cloudscape uses a 2px hairline for the crispest control insets (e.g. the gap inside a checked radio dot, focus-ring inner offset). Not a layout value; reserved for control-internal detail only. Carried verbatim from Cloudscape so native-looking controls are reproducible.
- `--space-s` = **12px** and `--space-l` = **20px** — the two non-4-multiple Cloudscape anchors. They are load-bearing for AWS-native fidelity: field vertical padding settles at ~5–12px and button/container horizontal padding at 20px in the Visual Refresh theme. Using 8px or 16px instead visibly de-AWS-ifies the controls. Kept as named exceptions rather than forcing the grid.

These two exceptions are the design-system's only deviations from the 8-point grid and exist solely to match the Cloudscape control rhythm; surface phases must consume the tokens, not reintroduce ad-hoc pixel values.

## Token Cascade & Theming Engine

**This section is the actual deliverable of Phase 1** (the template has no slot for it). It is the implementable contract for FND-01, FND-03, THM-03, THM-05 — the gate every later surface inherits.

### 1. Token cascade precedence (LOCKED — STATE.md, ROADMAP SC1)

CSS resolves the active theme through three layers, in this order. `:root` base = **light** (also the universal fallback) → OS-dark via media query → explicit `data-theme` override (beats OS).

```css
/* tokens.css */

/* (1) LIGHT defaults + universal fallback */
:root {
  --color-bg-container: #ffffff;
  --color-text-body: #0f141a;
  /* …all semantic tokens at their LIGHT values… */
  color-scheme: light;            /* THM-05 — see §3 */
}

/* (2) OS dark — applies ONLY when the user has NOT forced a theme */
@media (prefers-color-scheme: dark) {
  :root:not([data-theme="light"]):not([data-theme="dark"]) {
    --color-bg-container: #161d26;
    --color-text-body: #c6c6cd;
    /* …dark overrides… */
    color-scheme: dark;
  }
}

/* (3) Explicit manual override — beats OS preference */
:root[data-theme="dark"] {
  --color-bg-container: #161d26;
  --color-text-body: #c6c6cd;
  /* …dark overrides… */
  color-scheme: dark;
}
:root[data-theme="light"] {
  /* Token values already inherit from :root, so they need NOT be redeclared
     here. The one property this block MUST carry is color-scheme: light —
     so a user who forces Light on a dark-OS device gets light native controls
     (radios, checkboxes, scrollbars), which would otherwise follow the OS. */
  color-scheme: light;
}
```

**CRITICAL correctness detail (planner: do not omit):** the OS-dark block (2) MUST be guarded by `:root:not([data-theme="light"]):not([data-theme="dark"])`. Without both `:not()`s, a user who explicitly chooses **Light** while their OS is in dark mode would still get dark — the manual override would silently lose to the media query. The `:not()` guard is what makes "manual choice beats OS" true. This is the single most-misimplemented part of the cascade.

**Naming convention / namespace:** all tokens are CSS custom properties on `:root`, prefixed `--{category}-{role}[-{variant}]`:
- `--color-*` (text / bg / border / control / status, see Color section)
- `--space-*`, `--font-size-*`, `--line-height-*`, `--font-weight-*`, `--font-family-*`
- `--radius-*`, `--shadow-*`
- Dark theme **redeclares the same names** under selectors (2) and (3) — never a parallel `--color-bg-container-dark` name. One name, swapped value.

**`data-theme` lives on `<html>`** (`document.documentElement`), never `<body>` — so the attribute is set before `<body>` exists in the parse stream and the pre-paint script (below) can set it synchronously. This replaces the current `.darkMode` class on `<body>` (popup.js:79, options.js:195/197/221).

### 2. `theme-init.js` pre-paint contract (THM-03 — FOUC fix; LOCKED)

The existing FOUC bug (theme applied inside a post-`window.onload` async `chrome.storage` `.then()` — popup.js:76–79, options.js:194/220) is fixed by an **external, non-module** pre-paint script.

- **File:** `src/js/theme-init.js` — plain script (NOT an ES module, NO `type="module"`, NO imports). MV3/MV2 default CSP allows `'self'` external scripts; inline `<script>` is BLOCKED (PITFALLS #1). No `content_security_policy` key is added to any manifest; the default is the safe baseline. No CSP relaxation.
- **Placement:** **first child of `<head>`** on all 5 pages, BEFORE the `<link rel="stylesheet">` chain, so `data-theme` is set before first paint and before stylesheet-dependent render.
- **Logic (synchronous `localStorage` read — the only store fast enough for pre-paint):**
  ```js
  // src/js/theme-init.js  (non-module, runs synchronously in <head>)
  var m = localStorage.getItem('visualMode');
  // 'light' / 'dark' → set explicit attribute (beats OS);
  // anything else ('default', null) → remove attribute so the CSS @media branch decides.
  if (m === 'light' || m === 'dark') {
    document.documentElement.setAttribute('data-theme', m);
  } else {
    document.documentElement.removeAttribute('data-theme');
  }
  ```
- **Storage contract:** `localStorage['visualMode']` is the **same-device pre-paint cache**; `chrome.storage.sync['visualMode']` remains the **cross-device source of truth** (3-state `default`/`light`/`dark`, the existing key — unchanged). The write-through (`sync` + `localStorage` mirror) and live `storage.onChanged` update are **Phase 4** (THM-02/THM-04); Phase 1 only establishes the pre-paint *read* path and the attribute it sets. Phase 1 does NOT change any storage schema, key, or area.
- **Result (THM-03 acceptance):** zero flash of the wrong theme on any of the 5 pages on load; zero CSP violations in Chrome and Firefox consoles (no inline script, no CSP relaxation).

### 3. `color-scheme` per theme (THM-05 — native controls + scrollbars; LOCKED)

`color-scheme` is set on `:root` per theme (shown in §1): `light` in the `:root` base + `[data-theme="light"]`; `dark` in the `@media` dark branch + `[data-theme="dark"]`. This makes native form controls (radios, checkboxes, `<input type=color>`, `<select>`, textarea) and default scrollbars follow the active theme on **Chrome, Firefox, and Edge** — closing the cross-browser gap where the current WebKit-only `::-webkit-scrollbar` dark styling (popup.html:119–127) leaves Firefox/Edge with light native widgets in a dark page (PITFALLS #6).

Custom scrollbar styling, if retained, must pair `scrollbar-color` / `scrollbar-width` (Firefox) with `::-webkit-scrollbar` (Chrome/Edge) — or rely on `color-scheme` native themed scrollbars and drop custom scrollbar CSS. Foundation default: rely on `color-scheme`; keep the existing `scrollbar-width: thin` (popup.html:52).

### 4. `:focus-visible` ring — single tokenized treatment (consumed by every later surface)

One reusable, theme-aware focus indicator authored in `base.css`, keyed off the accent border token. No blanket `outline: none` anywhere without this replacement (PITFALLS #7, A11Y-01).

```css
/* base.css */
:focus-visible {
  outline: 2px solid var(--color-border-focus);   /* blue-600 light / blue-400 dark */
  outline-offset: 2px;
  border-radius: var(--radius-focus-ring);          /* 4px */
}
```

This is the contract for A11Y-01 across all surfaces; surface phases must not override it with a weaker treatment.

> **Expected visible delta in Phase 1 (not a regression):** because `base.css` ships this global `:focus-visible` ring and is linked from all 5 pages in Phase 1, the focus-ring appearance on the popup / options / auxiliary pages will visibly change in Phase 1 — *before* those surfaces are otherwise restyled (Phases 2–3). This is intended per ROADMAP SC2 (the foundation must prove primitives render in both themes). The Phase 1 plan should call this out so a reviewer does not flag it as "Phase 1 touched the popup". No other visual change to those surfaces occurs in Phase 1 (their inline `<style>` blocks and `.darkMode` rules are removed per surface in Phases 2–3).

### 5. File / asset layout & `<head>` wiring order (LOCKED — STATE.md, ROADMAP SC4)

**New files:**
```
src/css/
  tokens.css       # :root token layer + light/dark cascade (shared by ALL 5 pages)
  base.css         # reset, box-sizing, system-font typography, link/focus base, :focus-visible ring (shared)
  components.css   # reusable component shells: buttons, inputs, role-list item, panes,
                   #   status/empty/loading/error state containers — all consuming var(--token) only
src/js/
  theme-init.js    # external non-module pre-paint setter (§2)
```

`tokens.css` + `base.css` + `components.css` are **shared across all 5 entry points** → single source of truth; no per-page palette duplication. Surface-specific sheets (`popup.css`, `options.css`, `pages.css`) are introduced in Phases 2–3, not here.

**`<head>` wiring order — applied to ALL 5 pages (popup, options, supporters, credits, updated):**
```html
<head>
  <meta charset="UTF-8">
  <script src="js/theme-init.js"></script>     <!-- FIRST: pre-paint, non-module -->
  <link rel="stylesheet" href="css/tokens.css">
  <link rel="stylesheet" href="css/base.css">
  <link rel="stylesheet" href="css/components.css">
  <!-- (per-surface sheet added in later phases) -->
  <!-- existing page module script (e.g. options.js) stays where it is -->
</head>
```

**Per-page wiring deltas observed in current source (Phase 1 fixes these as part of the `<head>` contract):**
- `popup.html` — currently has **no `<!DOCTYPE html>`, no `<meta charset>`, no `<head>` script**; just an inline `<style>`. Phase 1 adds `<!DOCTYPE html>`, `<meta charset="UTF-8">`, the `theme-init.js` script first, and the `<link>` chain; the inline `<style>` block is removed in Phase 2 (popup surface), not here — but the token/base/components links and the pre-paint script land in Phase 1 so the foundation is wired.
- `options.html` — already has `<!DOCTYPE>`, `<meta charset>`, and `<script type="module" src="js/options.js">`. Add `theme-init.js` as the **first** head child (before that module script and before the links).
- `supporters.html` / `updated.html` — have `<!DOCTYPE>` + `<meta charset>`; add `theme-init.js` first + the `<link>` chain.
- `credits.html` / `updated.html` — currently have **no script in `<head>`**; they **gain** `<script src="js/theme-init.js"></script>` (explicitly called out in ROADMAP SC4).

The inline `<style>` blocks and the `.darkMode` class are **removed per surface in Phases 2–3** (popup → Phase 2; options/aux → Phase 3), not in Phase 1. Phase 1's job is to make the token system + pre-paint engine exist and be linked, and to prove (SC1) that toggling `data-theme` on `<html>` in devtools visibly re-skins a token-driven test element in both themes.

2. **`theme-init.js` must NOT be Rollup-bundled.** `build_test.sh`'s `for file in src/js/*` loop Rollup-bundles every top-level file in `src/js/`; `theme-init.js` would be caught by it and transformed (the project's Rollup runs `node-resolve`, which would likely emit a non-module script intact, but "likely" is not an acceptable contract for a pre-paint-correctness deliverable, and it mismatches how `build.sh` handles it). Skip it in the loop and copy it verbatim:
   ```bash
   for file in src/js/*; do
     if [ -f "$file" ]; then
       fname="${file##*/}"
       if [ "$fname" = "theme-init.js" ]; then continue; fi   # ship verbatim, not bundled
       rollup -c ./rollup.config.js src/js/$fname --file $destdir/js/$fname
     fi
   done
   cp src/js/theme-init.js $destdir/js/theme-init.js
   ```
   > **Gap surfaced for the planner:** ROADMAP SC5 only specified `cp -r src/css` for the test build and did not mention `theme-init.js` handling in `build_test.sh`. Because that loop would otherwise Rollup-process the pre-paint script, the verbatim-copy + skip-in-loop step above is required to keep the test build faithful to production. Plan it explicitly.

**No other build changes.** No `manifest.json` / `manifest_chrome.json` / `manifest_firefox.json` change, no `rollup.config.js` change, no new permission, no new host. (Preserves the fast store-review path — PITFALLS #8.)

### 7. Cross-browser floor note — `color-mix()` (PITFALLS, STACK §Version Compatibility)

If any **derived** value (e.g. a future per-profile-color reconciliation, Open Design Decision #1) is implemented with CSS `color-mix()`: `color-mix()` is Chrome 111+ / **Firefox 113+**, but the extension's manifest minimum is **Firefox 109**. Using `color-mix()` would silently raise the effective Firefox floor to 113. **Phase 1 uses NO `color-mix()`** — all token values are static hex, safe at FF 109. This is flagged here, in the foundation contract, because downstream phases will read theming rules from this document; prefer values/approaches that work at FF 109 (or move luminance math to JS) rather than introducing `color-mix()` into the token layer.
